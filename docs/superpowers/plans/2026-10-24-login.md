# Login (Telegram + email) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Sign in with Telegram or an email code, only when the user acts, with both methods linkable to one account and a minimal `/profile` page.

**Architecture:**
- Supabase Auth sessions via `@supabase/ssr` cookies. A `proxy.ts` refreshes them.
- **Email** uses Supabase's built-in OTP, sent through Resend.
- **Telegram:**
  - a server route verifies the widget's signature;
  - it maps the Telegram id to a Supabase user through a service-role-only `telegram_links` table;
  - it mints the session by exchanging a server-generated magic-link token.
- **UI:** a sign-in sheet opens over the form, so typed values stay mounted.

**Tech Stack:**
- Next.js 16.2 (App Router, `proxy.ts`), React 19
- `@supabase/ssr` 0.10, `@supabase/supabase-js` 2.103
- shadcn base-nova (`@base-ui/react` 1.4), Tailwind v4
- `node:crypto`, `node --test`

**Spec:** `docs/superpowers/specs/2026-10-24-login-design.md`

## Global Constraints

- **Secrets:** `SUPABASE_SERVICE_ROLE_KEY` and `TELEGRAM_BOT_TOKEN` are read only in `app/api/auth/telegram/**` route handlers, never in client code or any `NEXT_PUBLIC_` variable.
- **Telegram users' internal email:** `tg-<telegram id>@users.zakbis.com`, created confirmed, never shown and never mailed. The email field refuses any address ending in `@users.zakbis.com`.
- **Telegram data:** accepted only with a valid HMAC (key = SHA-256 of the bot token, data-check-string = the fields sorted by key except `hash`, joined `key=value` with `\n`, compared in constant time) and `auth_date` within 24 hours.
- **Profile:** reads use explicit columns, `select("id, first_name")`, never `*`. The name step shows whenever the user has no `profiles` row.
- **Exact copy:**
  - Sheet heading: "Sign in to send your request" or "Sign in to post your request".
  - Email button: "Email me a code".
  - Code prompt: "We sent a code to {masked email}".
  - Name step: "What should travelers call you?"
  - Conflict: "This email already has its own Zakbis account. Sign in with it instead." / "This Telegram account already has its own Zakbis account. Sign in with it instead."
  - Profile: "Add an email", "Connect Telegram", "Sign out".
- **Look and feel:** follow `DESIGN.md` (16px body text, green fills only for actions, existing `Field`/`Input`/`Button`).
- **The Telegram widget script** (`https://telegram.org/js/telegram-widget.js?22`) loads only when a Telegram button renders.
- **Commits:** only if the user asks. Applying `0002` to Supabase is additive and covered by the user's approval of this plan.

## Review Focus

1. **A Telegram payload replayed after 24 hours, or with any field changed** (name or photo), is refused with 401. → Task 1 tests.
2. **A Telegram id already linked to one account, used to "Connect Telegram" on a different account,** is refused with the conflict copy, and the existing link is untouched. → Task 2 SQL test (unique) and Task 4 route check.
3. **Signing in with Telegram for the first time while signed in by email** gets a separate account, not a hijack: the sign-in route never attaches to the current session, only the link route does. → Task 4.
4. **Closing the sheet after signing in but before entering a name:** the next action asks for the name again (no `profiles` row), and the form still holds its values. → Task 5 manual check.
5. **Typing `someone@users.zakbis.com` into the email field** is refused before any request to Supabase. → Task 1 test (`isInternalEmail`).

```ts

const good = sign({ id: 42, first_name: "Hana", auth_date: now - 60 }, "123:TEST");
test("valid payload", () => assert.equal(verifyTelegramLogin(good, "123:TEST", now)?.id, 42));
test("tampered field", () => assert.equal(verifyTelegramLogin({ ...good, first_name: "Eve" }, "123:TEST", now), null));
test("wrong token", () => assert.equal(verifyTelegramLogin(good, "999:OTHER", now), null));
test("older than 24h", () => assert.equal(verifyTelegramLogin(sign({ id: 42, first_name: "Hana", auth_date: now - 86_401 }, "123:TEST"), "123:TEST", now), null));
test("missing hash", () => assert.equal(verifyTelegramLogin({ id: 42, first_name: "Hana", auth_date: now }, "123:TEST", now), null));
test("internal email", () => { assert.equal(telegramEmail(42), "tg-42@users.zakbis.com"); assert.equal(isInternalEmail("X@Users.Zakbis.com"), true); assert.equal(isInternalEmail("a@gmail.com"), false); });
test("mask", () => assert.equal(maskEmail("meron@gmail.com"), "m•••@gmail.com"));
```

### Task 4: Telegram routes

**Files:**
- Create: `app/api/auth/telegram/route.ts` (sign in) and `app/api/auth/telegram/link/route.ts` (connect)

**Interfaces:**
- **Consumes:** `verifyTelegramLogin` and `telegramEmail` (Task 1), `telegram_links` (Task 2), and both `createClient` and `createAdminClient` (Task 3).
- **Produces:**
  - **`POST /api/auth/telegram`**, body = the widget's user object. Responses:
    - 401 `{ error: "invalid" }` when verification fails;
    - otherwise it sets the session cookies and returns 200 `{ hasProfile: boolean, firstName: string }`.
  - **`POST /api/auth/telegram/link`**, the same body, requiring a session. Responses:
    - 401 when there's no session or verification fails;
    - 409 `{ error: "taken" }` when the Telegram id is linked to another user;
    - otherwise 200 `{ linked: true }`.

- [ ] **Step 1: The sign-in route.** It does these steps in order:
  1. verify the payload (using `Date.now()/1000`);
  2. as admin, look up `telegram_links` by `telegram_id`;
  3. if there's no row: `admin.auth.admin.createUser({ email: telegramEmail(id), email_confirm: true, app_metadata: { telegram_id: id } })`, then insert into `telegram_links`;
  4. `admin.auth.admin.generateLink({ type: "magiclink", email: <that user's current email> })`, then on the cookie server client `auth.verifyOtp({ type: "magiclink", token_hash: link.properties.hashed_token })`;
  5. read `profiles` with `select("id, first_name")`.

  It never uses or modifies the current session's user.
- [ ] **Step 2: The link route.** It does these steps in order:
  1. get the user from the cookie client, returning 401 if there's none;
  2. verify the payload;
  3. as admin, upsert-guard: if a row exists for that Telegram id with a different `user_id`, return 409; if it exists for this user, return 200;
  4. otherwise insert the row and set `app_metadata.telegram_id` with `admin.auth.admin.updateUserById`.
- [ ] **Step 3:** Run `npm run lint && npm run build`. Expected: passes, and both routes are listed.
- [ ] **Step 4: Check bad input locally.** `curl -X POST /api/auth/telegram -d '{"id":1}'` should return 401. `curl -X POST /api/auth/telegram/link` with a valid-looking body and no cookie should return 401.
- [ ] **Step 5: Commit** (only if asked).
